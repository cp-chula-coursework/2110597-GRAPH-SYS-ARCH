# AX7010 Soul Battle - Pure Logic (1st Gen Console Project, variant C)

A third take on the course's "1st Gen game console" assignment
(05_PONG_History_and_Project.pdf). It plays the same battle as
[`../project01b_soulbattle`](../project01b_soulbattle) - your soul is a heart
you steer inside a battle box, dodging the enemy's attacks and striking back
with a timed hit - on the same board, at 640x480@60 over HDMI, with no CPU, no
software and no frame buffer.

The difference is what it draws with. **This version has no stored art at
all.** No sprite ROM, no character generator, no generated bitmaps: every
pixel on screen comes from arithmetic on the beam position. The enemy is a
hexagon with horns; the soul is two diamonds and a triangle; the blasters'
skulls are a shape function evaluated in the beam's own coordinates; the HUD
is bars, badges and Pong's own 5x7 digits.

```
                       /\        /\
                      /  \  /\  /  \       <- the enemy, ~12 comparisons:
                     +----\/--\/----+         hexagon, horns, core, eyes,
                     | (o)      (o) |         mouth, teeth
                     +--\ |#|#|#| /-+
                        \__________/
                                            88     <- damage, when you strike
             [##############------]  072    <- enemy HP: bar and number

        +--------------------------------------------+
        |                                            |  <- battle box
        |    |    |         |         |    |    |    |     260x160, 4 px
        |    |    |    <3   |         |    |    |    |     white frame
        |    |    |         |         |    |    |    |
        +--------------------------------------------+
                       /\                        <- phase band: a chevron for
                                                    your turn, hazard stripes
              [####################]  40         <- for the enemy's
```

## Why draw everything twice over?

Because that is the actual constraint the assignment is about. A 1st
generation console had no memory to keep a picture in - not a frame buffer and
not a sprite ROM either. Pong's ball, paddles and net are comparator outputs,
and even its score came out of a small diode ROM that could only make digits.
Everything on that generation's screens is either a shape a few gates can test
for, or a number.

`project01b` met the letter of that - no CPU, no frame buffer - but drew its
enemy, its soul and its skulls out of ROMs generated by a Python script, and
its messages out of an 8x16 ASCII font. That is 2nd generation hardware:
character generators and sprite ROMs are what the Atari 2600 and the arcade
boards of the late 70s added. This variant takes them all back out.

| | `project01b` | this project |
|---|---|---|
| soul | 16x16 sprite ROM, 2 frames | 2 diamonds + a triangle |
| enemy | 64x64 ROM at 2x | hexagon, horns, core, eyes, mouth |
| blaster skull | 32x32 ROM at 2x, 2 frames, 8 address symmetries | a shape in beam coordinates, 8 headings for free |
| bullets | comparator shapes | unchanged |
| text | 8x16 ASCII font ROM (96 glyphs) | none - shapes and digits only |
| numbers | the same font | project01's 5x7 `digit_font`, unchanged |
| stored art | 6,656 sprite pixels + 804 font rows | **0** |
| Verilog lines of ROM | 7,670 | **0** |

Nothing about the game itself changed: the same turn machine, the same six
attack waves, the same collision rules, the same testbenches passing.

## Everything on screen, and the arithmetic behind it

**The soul** ([`hdl/soul_renderer.v`](hdl/soul_renderer.v)) is three shapes in
a 16x16 cell, in half-pixel units so the centre falls between two columns:

```
  ax2 = |2*dx - 15|                            ....#......#....
  lobe_l = |dx-4|  + |dy-6| <= 6               ..#####..#####..
  lobe_r = |dx-11| + |dy-6| <= 6               ################
  lower  = dy >= 8 && ax2 <= 15 - 2*(dy-8)     ....########....
                                               .......##.......
```

The notch at the top and the full-width waist are where the two diamonds meet
- they are not drawn anywhere. The shattered heart for the losing screen is
the same shape with a two-pixel crack knocked out, the crack zigzagging with
`dy[2:1]`.

**The enemy** ([`hdl/monster_renderer.v`](hdl/monster_renderer.v)) mirrors
itself about its own centre column (`ax = |dx - 64|`), so only half of it is
ever described. The head is a hexagon whose half-width is a straight line in
`dy` - a slope is an add and a shift - the horns are bars whose centre walks
outward 3/8 px per row while their width shrinks to a point, the eyes are
windows cut by two diagonal half-planes (which is what makes them slant and
look angry), and the teeth are one bit of `dx`, a stripe every 4 px. Where
parts overlap, a priority mux picks the colour, so the eyes sit in front of
the head without either shape having to know about the other.

**The blasters** ([`hdl/blaster_renderer.v`](hdl/blaster_renderer.v)) are the
interesting one. The beam already worked in the blaster's own rotated frame -
`across` and `down`, picked from `dx`, `dy`, `dx+dy`, `dx-dy` by the heading -
so the skull is drawn in that same frame, once, facing along its own beam:

```
        uu=60  .-'''-.        dome    aa <= 24, rounded off past uu = 44
               |     |        jaw     aa <= 11 + uu/2, widening backwards
        uu=34  | O O |        sockets |aa-13| <= 8, cut by a diagonal
        uu=24  |  ^  |        nose    a small diamond
        uu=0   '|#|#|'        teeth   stripes, one bit of aa
                  V  the muzzle: where the beam comes out
```

All eight headings come out of that one description with nothing added. The
ROM version needed two stored frames plus mirror-and-swap address tricks to
get eight orientations out of them, and two overlapping skulls occluded each
other at cell granularity because they shared one ROM port; here each blaster
tests its own shape in parallel and they occlude pixel by pixel.

Two details the geometry forced:

- **The beam's `down` axis is not the skull's.** For a diagonal heading the
  beam measures how far along itself a pixel is with plain `dy` or `dx`, which
  is enough to know where to stop the beam. A skull drawn on that axis comes
  out *sheared* - sliced by horizontal lines while its sides run at 45
  degrees. So the skull computes a real along-beam axis, which on a diagonal
  is the other of the two sums (`dx+dy` where the beam uses `dx-dy`) - free,
  because both are already there.
- **The diagonal frame is sqrt(2) too big** in both axes, so the skull shrinks
  both by 0.6875 - three shifts and two adds, 2.8% off 1/sqrt(2) - and comes
  out the same size whichever of the eight ways it points. The beam applies
  the same correction the other way round, widening its half-width by ~1.375.

**The HUD** ([`hdl/hud_renderer.v`](hdl/hud_renderer.v)) has to say what the
game wants without being able to write it down, so each state gets a band
under the battle box instead of a sentence:

| state | band | inside the box |
|-------|------|----------------|
| TITLE | a blinking white bar | - |
| AIM / HIT | a chevron pointing up at the centre line | the sweeping cursor and its tier marks |
| DODGE | diagonal hazard stripes, one bit of `x + y` | bullets and blasters |
| WIN | a solid green bar | a green tick: two diagonal bands |
| LOSE | a solid red bar | a red cross: `\|across\|` or `\|along\|` under 5 |

The numbers are project01's `digit_font` - 5x7 glyphs for 0-9 and nothing
else, exactly what Pong's scoreboard could do. Player HP and enemy HP are
drawn at 2x beside their bars, and the damage from a strike at 4x above the
enemy's. Binary to decimal is four conditional subtractions (`>= 80`, `>= 40`,
`>= 20`, `>= 10`), which is how a hardwired scoreboard did it before dividers
were something to spend gates on.

The four digit fields sit on disjoint scanlines and every digit cell is a
power of two wide, so one `digit_font` serves all of them: the field picks
which number, the cell index is a shift of `x`, and the glyph row and column
are the low bits.

## Adaptation from the course slides: VGA -> HDMI

Same as the other projects in this repo. The AX7010 has no VGA DAC, so the
final stage is the pure-Verilog HDMI/TMDS pipeline built in
[`../demo_test_pattern`](../demo_test_pattern) - `hdmi_tx.v` +
`tmds_encoder.v` + `oserdes_tmds.v`, reused byte-for-byte, with
`vga_timing.v` in front of it exactly as in project01.

## Controls

The board's 4 push buttons (active-low). Four-way movement needs all four, so
there is no spare reset key - the battle restarts through the attract screen
instead.

| Button | Pin | Function                                          |
|--------|-----|---------------------------------------------------|
| key[0] | N15 | Move up    / confirm (start, strike, continue)    |
| key[1] | N16 | Move down  / confirm                              |
| key[2] | T17 | Move left  / confirm                              |
| key[3] | R17 | Move right / confirm                              |

The four board LEDs (M14, M15, K16, J16) show the player's HP a quarter at a
time. On the attract screen, where HP is always full, they echo the four
external buttons instead.

### External buttons (optional)

Five plain push buttons on expansion connector J10, each shorting its pin to
ground - no supply, no resistors, nothing that can be driven into a pin that
would not survive it.

| Button | J10 pin | Package pin |
|--------|---------|-------------|
| up | 3 | W19 |
| down | 4 | W18 |
| left | 5 | R14 |
| right | 6 | P14 |
| confirm | 7 | Y17 |
| common ground | 1 | - |

J10 numbers the opposite way round from J11: its pin 1 is at the **bottom**,
marked by the square pad, and pin 2 is 5V - leave that one alone.

### PlayStation controller through a serial adapter (optional)

The way a controller actually reached this design. The adapter is a board with
its own microcontroller: it talks the PlayStation protocol to the pad and
sends the result on as plain serial, so the FPGA needs one input pin and a
UART receiver rather than four pins and bit-level timing.

| Adapter pin | Goes to | J10 pin | Package pin |
|-------------|---------|---------|-------------|
| TXD | `uart_rx_pin`, through ~1k | 8 | Y16 |
| GND | header GND | 1 | - |
| VCC | header **3.3V** | 39 or 40 | - |
| RXD | leave unconnected | - | - |

Power it from 3.3V rather than the 5V on pin 2: at 3.3V its TXD swings 3.3V
and can be wired straight in.

This particular adapter sends one byte per button rather than the 8-byte
packet its documentation describes, at 9600 baud:

| Byte | Button | | Byte | Button |
|------|--------|-|------|--------|
| `41` | up | | `49` | triangle |
| `42` | down | | `4a` | cross |
| `43` | left | | `4b` | square |
| `44` | right | | `4c` | circle |

All four face buttons confirm, as do the neighbouring codes the shoulder
buttons and START land on. Nothing says when a button is released, so
`serial_pad.v` gives each button a timer that an arriving byte reloads and the
frame tick counts down; a button reads as held while its timer runs.

Without a text font there is nowhere to print the bytes themselves, so what
survives of project01b's on-screen read-out is what was actually used by the
end of bring-up - a row of lamps in the top-left corner:

```
  4  [][][][][]  []
  |   |            \_ red if frames are arriving without a stop bit
  |   \_ one lamp per decoded button: up down left right confirm
  \_ the selected baud rate, 0 = 9600 ... 4 = 115200
```

Holding left and right together for three quarters of a second steps the baud
rate and restarts the error count - a wrong rate shows as the red lamp lit and
no buttons moving, a dead wire as nothing happening at all.

### PlayStation controller, wired directly (optional)

`ps2_pad.v` polls a controller on the expansion header once per frame and ORs
the result in with the board buttons, so neither input has to be present.

> **Status: written and simulated, superseded on hardware by the serial
> adapter above.** It passes its testbench against a model of a real
> controller and the game runs with or without one plugged in, but on this
> board the DATA pin never registered being earthed, on any of three pins
> tried, even though the same pin drove out correctly. The four board buttons
> play the game in full, so this is an extra rather than a dependency.

| Wire   | Signal      | Direction   | Connect to        | Package pin |
|--------|-------------|-------------|-------------------|-------------|
| brown  | DATA        | pad -> FPGA | `IO2_2N`          | F20         |
| orange | COMMAND     | FPGA -> pad | `IO2_1N`          | F17         |
| yellow | ATTENTION   | FPGA -> pad | `IO2_2P`          | F19         |
| blue   | CLOCK       | FPGA -> pad | `IO2_1P`          | F16         |
| black  | GND         | -           | header GND        | -           |
| red    | 3.3V        | -           | header 3V3        | -           |

DATA is open drain and needs a pull-up; the XDC turns the FPGA's internal one
on. Power a breakout board from 3.3V, not 5V - the Zynq's IO is not 5V
tolerant. The 7V rumble line and ACKNOWLEDGE stay unconnected.

## How the battle plays

```
  TITLE --press--> AIM --press--> HIT --> DODGE --+--> AIM ...
                    ^                             |
                    |            enemy HP = 0 --> WIN  --press--> TITLE
                    |           player HP = 0 --> LOSE --press--> TITLE
```

- **AIM (your turn).** A cursor sweeps across the battle box at 7 px/frame.
  Press any button to stop it: the closer to the yellow centre line, the more
  damage (16 / 12 / 8 / 5 / 3), scored from the distance to the middle. The
  grey marks show the scoring tiers.
- **HIT.** The damage appears in digits above the enemy for 75 frames while it
  shakes and flashes white, and the green enemy HP bar drops.
- **DODGE (enemy turn).** Bullets spawn from the edges of the box for 330
  frames; you steer the soul at 3 px/frame in any of eight directions.
  Touching a bullet costs 2 HP and gives 60 frames of mercy invincibility,
  during which the heart blinks. The wave pattern cycles every turn:
  - **wave 0** - pillars falling from the top at random x
  - **wave 1** - pillars swiping in from the left or right at random y
  - **wave 2** - orbs dropping diagonally and bouncing off the side walls
  - **wave 3** - blasters: skulls that appear on the rim of the box, turn to
    face your soul, give you a moment's warning, and fire a beam straight down
    the line they are aiming along; this wave fires no bullets at all
  - **wave 4** - blasters again, sweeping a circle around the soul three times
    as fast
  - **wave 5** - one crimson blaster at a time, slow and heavily telegraphed,
    whose beam ends the battle outright

  Spawns get 2 frames closer together each turn, floored at 8.
- **WIN / LOSE.** Enemy at 0 HP wins the battle; your 40 HP running out ends
  it. Either way the screen holds for 90 frames, then any button returns to
  the attract screen for a rematch.

A full win takes eight perfect strikes (16 x 8 = 128 >= 120 HP) with seven
enemy turns in between, so one battle runs about a minute - long enough for
the wave cycle to come all the way round to the blasters and start over.

**How a blaster aims.** The heading is picked from eight compass points, and
then the muzzle is *solved for*: given a soul centre and a heading, there is
exactly one point on the rim of the box that a ray of that heading reaches the
soul from. For the four axis headings that is the soul's own x or y carried
out to the edge; for the four diagonals it is the soul's centre walked back
along the 45-degree line until it meets the nearer edge, `t = min(dx, dy)` -
subtractions and one comparison, no multiplier and no divider. The muzzle
keeps re-solving every frame while the blaster fades in, so the skull visibly
slides along the rim after you, and freezes the moment the warning line
appears.

## Hardware structure

Everything runs at the 25.175 MHz pixel clock. `battle_logic` updates the
whole game once per frame during vertical blanking (36,000 pixel clocks are
available; it uses one), so the renderers never see state change mid-frame.

```
                              x,y
  vga_timing --> +---------+---------+---------+---------+---------+
                 |         |         |         |         |         |
                 v         v         v         v         v         v
          soul_renderer  blaster_  bullet_   hud_      monster_
          (2 diamonds +  renderer  renderer  renderer  renderer
           a triangle)   (beam +   (pillars  (bars,    (hexagon,
                          skull in  and orbs) badges,   horns, eyes,
                          beam                digits)   teeth)
                          coords)
                 |         |         |         |         |
                 +---------+---------+---------+---------+
                                    |
        compositor: soul > blasters > bullets > HUD > enemy > black
                    (every layer has the same 2-clock latency)
                                    |
                          vid_r/g/b + syncs ---> hdmi_tx

  battle_logic ----- soul_x/soul_y, state, wave ----> blaster_logic
       ^                                                   |
       +--------- blast_hit, blast_busy -------------------+
```

| File | Role |
|------|------|
| `top.v` | clocking IP + core + HDMI transmitter |
| `battle_core.v` | timing, layers, compositor, enemy bob/shake |
| `battle_logic.v` | the turn machine, bullet register file, collisions, LFSR |
| `blaster_logic.v` | the blaster wave: heading choice, muzzle solve, phase timers |
| `blaster_renderer.v` | beam half-plane tests + the skull, drawn in beam coordinates |
| `soul_renderer.v` | the heart, whole and shattered |
| `monster_renderer.v` | the enemy, six shapes and a priority mux |
| `bullet_renderer.v` | 8 parallel bullet shape tests + priority mux, clipped to the box |
| `hud_renderer.v` | box frame, both HP bars, attack cursor, state badges, numbers |
| `digit_font.v` | 5x7 digits 0-9, reused verbatim from project01_pong |
| `pad_input.v` | 4-button synchronizer + debouncer, as in project03 |
| `ps2_pad.v` | PlayStation controller host: SPI mode 3, LSB first, one poll per frame |
| `uart_rx.v` | 8N1 serial receiver, baud selectable on the board |
| `serial_pad.v` | serial adapter bytes -> held button levels |
| `vga_timing.v`, `hdmi_tx.v`, `tmds_encoder.v`, `oserdes_tmds.v` | unchanged from project01 |

Notes on the design decisions a hardwired console forces:

- **Bullets are a register file, not a display list.** Eight fixed slots of
  {x, y, vx, vy, type, active}; the per-frame update is an unrolled loop and
  the renderer tests all eight in parallel, then priority-muxes the pixel.
- **Every layer is a shape test.** With no ROM anywhere, no layer has a memory
  port to share or to wait on, so all five of them are combinational logic
  plus two register stages - which is why the compositor can stay a plain
  priority mux.
- **All layers have the same 2-clock latency**, so the sync signals just ride
  a matching 2-stage delay.
- **A circling attack for free.** The ring wave needed no sine table, no
  multiplier and nothing new in the renderer: with the heading already
  quantized to eight compass points, sweeping a circle is a counter that steps
  by one.
- **Eight headings, so a beam is still just a comparator.** With the aim
  quantized to the compass points, "inside the beam" is `|across| <= width`
  and `0 <= down <= reach`, where `across` and `down` are `dx`, `dy`, `dx+dy`
  or `dx-dy` picked by the heading - four adders and four comparators per
  blaster, and no rotation, normalization or multiplier anywhere.
- **Not one multiplier and not one divider in the design.** Every slope,
  scale and taper in the artwork is a shift and an add: 1.5 px per row is
  `v + (v >> 1)`, 3/8 is `(v + (v << 1)) >> 3`, and 1/sqrt(2) is
  `(v >> 1) + (v >> 3) + (v >> 4)`.
- **The controller is polled in vertical blanking**, on the same `frame_start`
  tick the game logic runs on, so the game never has to wait on a serial bus.

## Verification

Before targeting hardware:

- `sim/tb_battle_logic.v` drives the game logic with synthetic frame pulses
  and plays the battle out twice through the real button interface: once
  winning with bullseye strikes while a small avoidance policy plays the seven
  enemy turns that takes, once losing with weak strikes and no dodging at all.
  It checks the win and loss paths, restart-from-title, the scoring tiers, the
  wall clamps and diagonal movement, that a hit costs exactly 2 HP and cannot
  repeat inside the mercy window, and that the blaster waves fire no bullets,
  hit a soul that stands still, and do not hand the turn back with a blaster
  still on screen.
- `sim/tb_blaster.v` drives `blaster_logic` directly, which is what makes the
  aiming geometry checkable exactly rather than by eye: with the soul held
  still, the ray from every live muzzle passes precisely through the soul's
  centre, for all eight headings; every muzzle lands on the rim of the box; no
  muzzle is closer than the 40 px minimum lead; the phases run TRACK ->
  CHARGE -> FIRE -> FADE; and the ring and crimson variants behave.
- `sim/tb_blaster_draw.v` dumps the blaster layer on its own with all eight
  headings placed at once - the beams should all meet on the soul marker and
  each skull should point down its own beam, at the same size on the diagonals
  as on the axes. That last part is what the beam-coordinate skull has to get
  right and a sprite ROM never had to.
- `sim/tb_soulbattle.v` runs the whole core at real 640x480@60 timing, checks
  the video timing the HDMI encoder depends on (exactly 640x480 active pixels
  and 525 lines per frame), and dumps one frame of each screen (title / aim /
  hit / dodge) as PPM images for visual inspection.
- `sim/tb_uart_rx.v` and `sim/tb_ps2_pad.v` cover the two controller paths -
  bytes at the wrong rate, framing errors and glitches for the first, a model
  of a real controller answering (or not being plugged in) for the second.
- The full `top.v` hierarchy elaborates cleanly under `iverilog` (the only
  errors are for Xilinx's `OSERDESE2`/`OBUFDS` primitives and the
  Vivado-generated `clk_wiz_video` IP, neither of which exist outside
  Vivado/its simulator - expected and harmless).

```sh
iverilog -o /tmp/tb_logic.vvp hdl/battle_logic.v hdl/blaster_logic.v \
  sim/tb_battle_logic.v
vvp /tmp/tb_logic.vvp

iverilog -o /tmp/tb_blaster.vvp hdl/blaster_logic.v sim/tb_blaster.v
vvp /tmp/tb_blaster.vvp

iverilog -o /tmp/tb_bd.vvp hdl/vga_timing.v hdl/blaster_renderer.v \
  sim/tb_blaster_draw.v
vvp /tmp/tb_bd.vvp     # writes soulbattle_blaster*.ppm

iverilog -o /tmp/tb_ps2.vvp hdl/ps2_pad.v sim/tb_ps2_pad.v
vvp /tmp/tb_ps2.vvp

iverilog -o /tmp/tb_uart.vvp hdl/uart_rx.v sim/tb_uart_rx.v
vvp /tmp/tb_uart.vvp

iverilog -o /tmp/tb_sb.vvp hdl/vga_timing.v hdl/pad_input.v hdl/digit_font.v \
  hdl/soul_renderer.v hdl/monster_renderer.v hdl/bullet_renderer.v \
  hdl/blaster_renderer.v hdl/hud_renderer.v hdl/battle_logic.v \
  hdl/blaster_logic.v hdl/ps2_pad.v hdl/uart_rx.v hdl/serial_pad.v \
  hdl/battle_core.v sim/tb_soulbattle.v
vvp /tmp/tb_sb.vvp     # slow: real frames, writes soulbattle_*.ppm
```

This does not replace testing on real hardware - build the project and confirm
the battle plays correctly on an HDMI display before submitting.

## Building the project

From a terminal, with Vivado on your `PATH`:

```sh
cd project01c_soulbattle
vivado -mode batch -source scripts/create_project.tcl
```

This creates a Vivado project under `project01c_soulbattle/vivado_project/`
(git-ignored) with all sources, constraints, and the clocking IP added. It
does not run synthesis. Open the generated project in the Vivado GUI, then:

1. Run Synthesis
2. Run Implementation
3. Generate Bitstream
4. Open Hardware Manager, connect to the board (JTAG), and program the device

If you'd rather create the Clocking Wizard IP by hand in the GUI instead of
running the script: component name `clk_wiz_video`, input clock 50 MHz on
`clk_in1`, enable `clk_out1` = 25.175 MHz and `clk_out2` = 125.875 MHz.
