# AX7010 2D Platformer (3rd Project: Background tile)

A hardwired NES/SNES-style tile-map platformer over HDMI for the course's
"Background tile" assignment (10_2D_Platformer_FPGA_Project.pdf): no CPU, no
software - a tile map ROM, tileset ROM, sprite ROM, and a per-frame game
state machine in pure Verilog, following the slides' architecture through
section 4 (tiles -> scrolling -> single sprite) plus the "use state machine
to do simple game logic" requirement:

- **Scrolling tile background** - 80x30 tile map (2 screens wide, scrolls on
  the x axis per the slides), 16x16-pixel tiles from a 32-entry tileset.
- **Animated player sprite** - 32x32, 4 frames (idle, 2-frame walk cycle,
  jump), horizontally mirrored when facing left, pure white `12'hFFF` =
  transparent, exactly as the slides define the "Mario ROM". The art is
  original (drawn in `scripts/gen_assets.py`), since the slides' actual
  Mario sprites are copyrighted.
- **Game logic in a state machine** - gravity with variable-height jumps,
  walk/run, pixel-perfect map collision through a dedicated collision ROM
  port (the slides' `coll_rom`), pits that respawn you at the start, and a
  camera that follows the player - all one `always @(posedge clk)` FSM that
  runs once per frame during vertical blanking.

The multi-sprite renderer with the double line buffer and topRAM/vRAM
(slides sections 5-6) belongs to the 4th project (PPU) and is intentionally
not part of this one.

## Adaptations from the course slides

Board-driven adaptations, with the taught architecture kept as-is:

- **VGA -> HDMI** (as in [`../project01_pong`](../project01_pong)): the
  slides' reference design outputs VGA from a Basys3; the AX7010 only has
  HDMI. The standard `vga_timing.v` + `hdmi_tx.v`/`tmds_encoder.v`/
  `oserdes_tmds.v` pipeline from the earlier projects is reused unchanged.
- **100 MHz -> pixel clock**: the slides run logic at 100 MHz (4 clocks per
  pixel) and let the 2-clock BRAM latency hide inside one pixel. Here
  everything runs at the 25.175 MHz pixel clock (as in project02), so the
  sync/blank flags ride a matching 2-stage pipeline instead and leave
  aligned with the RGB - the frame just shifts 2 pixels, invisibly.
- **$readmemh -> generated Verilog**: the slides load `.mem` files with
  `$readmemh`; here the three graphics ROMs are Verilog files generated by
  `scripts/gen_assets.py` with the pixel data in `initial` blocks, so
  synthesis and simulation see identical contents with no file-path issues.
- **Buttons for a controller**: left / right / jump / run on the board's 4
  push buttons, debounced (no typematic repeat - the game logic samples
  held levels once per frame and derives its own jump edge).

## Architecture (per the slides, sections 2-4 + 6)

```
                x,y --------------------------+----------------+
 vga_timing --> (+ scrollOffset) = x_scroll   |                |
  640x480@60        |                |        |           hs/vs/blank
                    v                v        v            2-stage
              x_scroll[10:4]   x_scroll[3:0]  player state    delay
              y[9:4]           y[3:0]         (posX,posY,        |
                    |                |         frame,flip)       |
                    v                v            |              |
                map_rom --tile--> bg_tile_rom  player_rom        |
               (80x30x8)         (32x16x16x12) (4x32x32x12)      |
                 1 clk              1 clk         + window test  |
                    \                |                |          |
                     \               v                v          |
                      +---->  compositor: sprite over bg,        |
                              12'hFFF = transparent              |
                                        \                        v
                                         +------> vid_r/g/b, syncs

 game_logic: per-frame FSM during vblank                  map_rom (2nd
   input -> gravity -> move X -> collide X ->  probes --> instance =
   move Y -> collide Y -> camera -> animation             the coll_rom)
```

- **`map_rom.v`** (generated) - the slides' Map ROM: 80x30 8-bit tile
  indices, `addr = row*80 + col`. Two screens wide; a `scrollOffset`
  register is added to the VGA x exactly as in slide section 3.
  Instantiated twice: renderer + collision (the slides' `coll_rom`), so the
  game logic never contends with the pixel pipeline for the read port.
- **`bg_tile_rom.v`** (generated) - the slides' BG ROM: 32 tiles of 16x16,
  12-bit RGB, `addr = {tile, y[3:0], x[3:0]}`. Tile index bit 4 doubles as
  the *solid* attribute (0-15 decorative sky/clouds/bushes, 16-31 solid
  ground/brick/pipe...), which is what the collision FSM tests.
- **`player_rom.v`** (generated) - the slides' Mario ROM with original art:
  4 frames of 32x32, `12'hFFF` transparent.
- **`bg_renderer.v`** - map fetch (1 clk) -> tile pixel fetch (1 clk), with
  the active-area guard so the map index can never leave the 80x30 grid.
- **`player_renderer.v`** - the slides' mario_renderer: window test in
  world coordinates (`x_scroll` vs `posX`), `offsetX = flip ? 31-dx : dx`
  mirror, same 2-clock latency as the background so the layers composite
  aligned.
- **`game_logic.v`** - the slides' section-6 FSM, run once per frame at the
  start of vblank (~30 of the 36,000 available clocks): sample buttons ->
  jump impulse -> gravity (lighter while rising with jump held, for
  variable-height jumps) -> move/collide X (3 side probes) -> move/collide
  Y (2 support/head probes; landing snaps the hitbox flush) -> respawn if
  fallen off the map -> camera `scroll = clamp(posX+16-320, 0, 640)` ->
  sprite frame/facing. Vertical position is 1/8-px fixed point so gravity
  tunes finely at 60 fps. The 16x28 hitbox is inset in the 32x32 sprite.
- **`pad_input.v`** - 2-FF synchronizer + 5 ms counter debounce per button.
- **`platformer_core.v`** - wires the above together with the compositor;
  `top.v` adds the Clocking Wizard and the HDMI/TMDS output stage (reused
  unchanged from the previous projects).

## Controls

The board's 4 push buttons (active-low):

| Button | Pin | Function |
|--------|-----|----------|
| key[0] | N15 | Walk left |
| key[1] | N16 | Walk right |
| key[2] | T17 | Jump (hold for a higher jump) |
| key[3] | R17 | Run (hold while walking) |

The level: crates and a pipe to jump over, floating platforms to climb,
two pits (falling in respawns you at the start), a stone staircase, and a
metal pillar marking the end, 2 screens to the right.

## Graphics assets

All three `*_rom.v` files are generated by
[`scripts/gen_assets.py`](scripts/gen_assets.py) (original pixel art - the
tileset, the level, and the robot player are drawn in the script; no
copyrighted game assets). To tweak art or level layout, edit the script and
rerun:

```sh
python3 scripts/gen_assets.py                # regenerate hdl/*_rom.v
python3 scripts/gen_assets.py --preview out  # + PNG previews (needs Pillow)
```

## Verification

Before targeting hardware, everything below the clocking IP / TMDS output
was simulated with Icarus Verilog:

- `sim/tb_player_rom.v` dumps all 4 sprite frames as ASCII art
  (`player_dump.txt`) - eyeballed against the intended art.
- `sim/tb_platformer.v` simulates the complete core rendering real 640x480
  frames while an auto-runner plays the level through the debounced
  buttons: it verifies the spawn state, walking with facing flip and the
  world-edge clamp, stopping flush against a wall, jumping over the crate
  stack, falling into the first pit and respawning at the start, then a
  second run that jumps the pit and the pipe to reach the middle of the
  level - checking a camera invariant (`scroll == clamp(posX-304,0,640)`)
  and the airborne/walk/idle animation states on every frame. It also dumps
  two rendered frames as PPM images (`platformer_start.ppm`,
  `platformer_mid.ppm`) for visual inspection.
- The full `top.v` hierarchy elaborates cleanly under `iverilog`; the only
  unknown modules are Xilinx's `OSERDESE2`/`OBUFDS` and the Vivado-generated
  `clk_wiz_video` IP, as expected outside Vivado.

Run them from the project root:

```sh
iverilog -o /tmp/tb_prom.vvp hdl/player_rom.v sim/tb_player_rom.v && vvp /tmp/tb_prom.vvp
iverilog -o /tmp/tb_plat.vvp hdl/vga_timing.v hdl/pad_input.v hdl/map_rom.v \
  hdl/bg_tile_rom.v hdl/player_rom.v hdl/bg_renderer.v hdl/player_renderer.v \
  hdl/game_logic.v hdl/platformer_core.v sim/tb_platformer.v && vvp /tmp/tb_plat.vvp
```

(The second one simulates ~1000 video frames and takes several minutes.)

This does not replace testing on real hardware - build the project and
confirm it works on an HDMI display before submitting.

## Building the project

From a terminal, with Vivado on your `PATH`:

```sh
cd project03_platformer
vivado -mode batch -source scripts/create_project.tcl
```

This creates a Vivado project under `project03_platformer/vivado_project/`
(git-ignored) with all sources, constraints, and the clocking IP added. It
does not run synthesis. Open the generated project in the Vivado GUI, then:

1. Run Synthesis
2. Run Implementation
3. Generate Bitstream
4. Open Hardware Manager, connect to the board (JTAG), and program the device

If you'd rather create the Clocking Wizard IP by hand in the GUI instead of
running the script: component name `clk_wiz_video`, input clock 50 MHz on
`clk_in1`, enable `clk_out1` = 25.175 MHz and `clk_out2` = 125.875 MHz.
